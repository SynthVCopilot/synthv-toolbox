# 调研结论

- [重复下载] -> 普通槽位通过完整根目录重命名切换 -> `databases` 随槽位移动，因此每个槽位各自保存声库缓存。
- [并发数据] -> 每次准备或启动并发实例均将共享路径设为当前 canonical 根 -> 所有盒子只能临时共享当前活动槽位的 `databases`，而不是稳定的全局数据源。
- [授权边界] -> 账号预检从官方许可响应提取产品名 -> 本地数据库只能证明安装内容，不能证明登录账号拥有授权。
- [路径风险] -> 并发副本位于长的 AppData 槽位路径下 -> 需要缩短 Sandboxie 文件、注册表与 IPC 根，同时保留受管目录和标记校验。
- [缓存授权] -> 本地数据库与会话扩展内容不包含可安全验证的授权映射 -> 只允许将成功官方预检得到的脱敏结果作为未来的“历史观测”，本次不把安装缓存误作账号授权。
- [共享迁移] -> 不同槽位的同路径文件先按字节比较 -> 仅在完全相同或不存在时合并；任何冲突都会停止，不覆盖任一文件。
- [路径长度] -> Sandboxie `FileRootPath` 需要稳定绝对路径 -> 不使用相对路径，改用 `c\\<UUID 前缀>` 并保留完整 UUID 标记校验；旧布局在下次准备或启动时同卷移动。
- [迁移占用] -> 首次共享化会替换槽位内的数据库目录 -> 仅当迁移确有必要且普通、隔离实例均不在运行时才允许继续。
