# 作词与音频导入工作流指导

> 状态：方案评估与实施指导
>
> 适用项目：SynthV Toolbox

## 结论

这个方向值得做，但目标应定义为“受控的歌曲作词工作台 + 本地音频导入管线”，而不是把工具做成通用视频下载器或自动写歌机器人。

当前仓库已经具备一部分基础：歌词草稿本机自动保存、段落结构模板、中文韵脚查询、可选的 AI 候选、工作流历史、工程检查点，以及带 SHA-256 校验的串行组件下载队列。缺口在于这些能力还没有围绕同一个歌曲项目闭环，平台音频也还没有安全的 URL 导入入口。

建议的完整闭环如下：

```text
用户提供本地文件或 URL
        ↓
来源/权利确认 → 元数据预览 → 受管理下载暂存
        ↓
音频标准化 → BPM/拍点/调性/人声与结构分析
        ↓
歌曲项目 → 段落 → 旋律音节槽位 → 歌词版本
        ↓
韵脚/音节/发音/重复度检查 → 人工试听与修改
        ↓
导出歌词、LRC、逐字 LRC、MIDI 或 SynthV 工程副本
```

## 现状评估

### 已有能力

- `main.ts` 已有作词页面、草稿自动保存、段落预设、韵脚查询和 AI 候选 UI。
- `lyric_tools.rs` 已有中文韵脚字典查询、结构模板限制、候选输入校验和结果解析。
- `creative_history.rs` 已有工作流历史、工程检查点和报告导出基础。
- `components.rs` 已有 FFmpeg、pi-audio、CVRS 和 Sandboxie 的组件状态/安装/删除路径。
- `downloads.rs` 已有串行队列、活动任务去重、下载与删除互斥。
- 本地音频工作流已经有权利确认字段，说明素材权利可以成为所有外部导入流程的统一门槛。

### 关键缺口

- 草稿保存在浏览器 `localStorage`，没有歌曲项目、版本、音频来源和工程检查点之间的持久关联。
- 结构模板只有“行数/韵脚格式”，没有小节、拍点、音节数、重音、音高或发音槽位。
- AI 只能生成候选句，不能基于旋律约束评分，也不能把候选安全地回写到 SynthV 音符歌词。
- 平台音频没有元数据预览、下载暂存、来源记录、可取消任务、失败重试和删除素材流程。
- 组件目录中列出了 Whisper、音高模型、人声分离等意向组件，但实际可信安装清单和运行接线尚未完成。
- 当前组件队列是内存态；应用重启后不能恢复未完成任务，也不能展示完整的组件版本和安装来源。

## 推荐产品边界

### 平台音频导入

第一版只接受用户主动粘贴的单个 Bilibili 或 YouTube URL，并执行以下步骤：

1. 解析并显示标题、作者、时长、可用音频格式和来源 URL。
2. 要求用户确认“我拥有这些内容，或已获得足够授权，并会遵守平台规则和适用法律”。
3. 只在本机下载到受管理的素材目录，不把音频上传到 Toolbox 服务。
4. 保留原始媒体、标准化 WAV、元数据快照、文件指纹和权利确认时间。
5. 允许用户取消、重试、打开素材位置和删除 Toolbox 管理的副本。
6. 下载完成后才允许进入 FFmpeg/pi-audio 分析；失败不应留下半成品被当作可用音频。

明确不做：

- 不做站内搜索、关键词爬取、频道批量抓取或定时抓取。
- 不采集或保存 Bilibili/Google Cookie、密码、令牌，也不提供登录态代持。
- 不绕过 DRM、付费墙、地区限制、访问控制或平台反自动化措施。
- 不把“公开可见”解释为“可下载、可改编或可商用”。
- 不在 UI、README 或营销文案中承诺任意 URL 永久可用。

YouTube 服务条款目前把下载、复制和自动化访问列为限制项，除非服务明确授权、取得书面许可或适用法律允许；Bilibili 也要求遵守平台协议、版权和内容使用限制，付费内容协议更明确禁止通过技术手段下载/传播。因此权利确认应是产品流程的一部分，而不是免责声明中的小字。参阅 [YouTube 服务条款](https://www.youtube.com/static?template=terms)、[Bilibili 协议汇总](https://www.bilibili.com/blackboard/topic/activity-cn8bxPLzz.html?mng_ts=1593598636731) 和 [Bilibili 付费内容协议](https://www.bilibili.com/blackboard/agreement-class-h5.html)。

### 下载组件

建议把平台导入实现为独立的 `media-fetcher` 组件，优先使用成熟的 yt-dlp，而不是把站点解析器写进 Rust 核心。yt-dlp 官方接口支持先提取元数据、再下载，并通过 FFmpeg/FFprobe 做音频抽取；它的站点适配会变化，所以必须被版本化、可替换和可禁用。参阅 [yt-dlp 官方 README](https://github.com/yt-dlp/yt-dlp/blob/master/README.md)。

组件清单至少包含：

| 字段 | 用途 |
| --- | --- |
| `id` | 稳定组件标识，例如 `media-fetcher` |
| `version` | 固定版本，不使用不可追踪的 `latest` |
| `platform` / `arch` | Windows/macOS 与 CPU 架构 |
| `source` | 官方发布页或仓库地址 |
| `downloadUrl` | 具体归档或可执行文件地址 |
| `sha256` | 下载后完整校验 |
| `license` | 组件许可证和归属 |
| `entrypoint` | 仅允许的可执行入口 |
| `capabilities` | 网络、文件、子进程等能力声明 |

现有 FFmpeg 的“固定版本 + 暂存目录 + SHA-256 + manifest + 原子替换”模式可以复用。Toolbox 内置下载器只获取固定清单中的可信组件包；媒体 URL 的解析/下载由 `media-fetcher` 自己执行，两者不要混成一个隐式下载器。

## 完整作词工作台

### 歌曲项目模型

建议新增一个本地歌曲项目，而不是继续把所有状态散落在页面变量中：

```text
SongProject
├─ project.json                 项目元数据、语言、创作简报、当前版本
├─ sources/                     来源 URL、权利确认、原始媒体与元数据快照
├─ audio/                       标准化音频、分析结果、人声/伴奏 stem
├─ structure/                   段落、小节范围、拍号、目标韵脚
├─ melody/                      音符槽位、音节数、重音和置信度
├─ lyrics/                     草稿、版本、候选采用记录
├─ checkpoints/                 可恢复快照
└─ exports/                    LRC、逐字 LRC、MIDI、SynthV 副本和报告
```

每次自动保存应生成轻量版本记录；完整音频和工程文件使用内容指纹去重。删除项目时必须明确区分“删除项目索引”“删除 Toolbox 管理的素材”和“保留用户原始文件”。

### 作词步骤

1. **建立创作简报**：语言、主题、叙事视角、情绪曲线、时代/场景、禁用意象、目标听众。
2. **建立结构**：前奏、主歌、预副歌、副歌、桥段、尾声等；可从现有预设开始。
3. **导入旋律约束**：优先读取 MIDI/SVP；音频则先给出 BPM、拍点和旋律候选，并标记低置信区间。
4. **生成音节槽位**：每个槽位包含开始/结束拍、建议音节数、重音位置、音高走向、语言和人工修订状态。
5. **写作与版本**：编辑器支持整段写作，也支持逐槽位填词；候选只能加入新草稿版本，不能静默覆盖当前稿。
6. **语言检查**：空音节、多音节拥挤、极短音符、混合语言、发音歧义、连续同字和不自然断句。
7. **韵脚与听感检查**：韵部只是提示，不得把押韵判定当成文学质量判定；主歌、副歌和桥段允许使用不同约束。
8. **人工确认与导出**：用户确认后导出普通歌词、LRC、逐字 LRC、带歌词 MIDI，或写入新的 SynthV 工程副本。

### AI 的职责

AI 只做可追踪的候选生成、改写建议、风险解释和候选排序。每次请求应携带最小必要上下文：当前段落、槽位约束、用户简报和用户明确选中的草稿片段；默认不上传完整工程、原始音频或平台 URL。

候选结果需保存：生成时间、输入约束摘要、使用的模型标识、候选文本、用户是否采用和采用后的版本。用户未点击采用前，候选永远不是正式歌词。

## 内部工具分层

所有工具都应有统一描述：`name`、`inputSchema`、`outputSchema`、`writes`、`network`、`requiredComponents`、`requiresConfirmation`、`failurePolicy`。

| 层 | 工具 | 默认网络 | 写入范围 |
| --- | --- | --- | --- |
| 纯本地分析 | 韵脚、音节、发音、歌词重复度、工程探测、报告生成 | 否 | 报告/索引 |
| 本地媒体 | FFmpeg 转码、pi-audio 探测、拍点/调性、音频裁切 | 否 | `audio/`、报告 |
| 本地工程 | LRC 导出、MIDI 生成、SynthV 副本、检查点 | 否 | 只写新副本 |
| 受控外部导入 | URL 元数据、媒体下载 | 是，用户主动触发 | `sources/`、`audio/` |
| AI 辅助 | 候选句、改写、风险解释 | 按模型配置 | 只写历史和新草稿版本 |
| 组件管理 | 下载、校验、安装、删除、打开安装包 | 是，固定来源 | `components/`、配置 |

建议先让桌面 UI 和 Copilot 共用同一套本地工具服务；工具不应通过前端拼接 shell 命令。路径必须由后端解析和限制，URL 必须使用明确协议和允许的站点集合，所有外部进程参数都应以参数数组传递。

## 组件自我管理设计

### 状态机

在现有状态基础上补充持久化和可恢复状态：

```text
queued → downloading → verifying → installing → ready
                  └→ failed ↺ retry
queued/downloading/installing → cancelling → cancelled
```

要求：

- 队列任务写入磁盘，应用重启后恢复为可重试状态。
- 同一个组件同一版本不能并行安装；安装和删除必须互斥。
- 下载写入随机暂存目录，校验通过后原子移动到最终位置。
- 组件目录必须有 manifest，缺少匹配版本/哈希时按外部目录保留。
- 删除只处理 Toolbox 明确拥有的目录和配置引用，永不删除用户输入、输出或系统安装。
- 失败信息必须区分网络失败、哈希失败、权限失败、依赖失败和组件自身退出码。
- 提供“重试”“打开日志”“打开位置”“清理缓存”四个明确动作；清理缓存前显示具体路径和大小。

### 管理页面

组件中心应显示：已安装版本、可用版本、来源、许可证、磁盘占用、最近一次校验、依赖组件、网络行为和卸载范围。对于 Sandboxie 这类需要驱动或系统交互的组件，继续只下载官方安装包并交由用户确认安装，不做静默安装。

## 分阶段实施建议

### 第一阶段：本地作词闭环

- 把歌词草稿从 `localStorage` 提升为歌曲项目文件。
- 复用现有段落、韵脚、发音诊断、历史和检查点。
- 增加版本、导入/导出和“只写新副本”的边界。
- 暂不引入平台 URL 下载，先用本地音频/MIDI/SVP 验证模型。

### 第二阶段：平台音频导入

- 新增 `media-fetcher` 固定版本组件和可信 manifest。
- 实现 URL 校验、元数据预览、权利确认、受管理下载、取消/重试和来源记录。
- 下载后的标准化 WAV 统一进入现有 FFmpeg/pi-audio 工作流。
- 只支持单 URL、公开且用户确认有权使用的素材。

### 第三阶段：旋律约束作词

- 增加拍点/小节/音节槽位模型。
- 先支持 MIDI/SVP 的确定性音符约束，再接入音频旋律候选。
- 为每句输出音节数、重音、发音风险和低置信提示。
- 将歌词导出和 SynthV 新工程副本连通。

### 第四阶段：完善组件和内部工具

- 依次接入 Whisper、本地音高识别、人声分离和批处理；每个组件都必须先有固定来源、版本、哈希、许可证和独立测试。
- 统一 UI/Copilot 工具协议和权限声明。
- 加入磁盘配额、缓存保留策略、崩溃恢复和离线模式。

## 验收标准

### 用户功能

- 没有外部组件时，用户仍可写作、保存、恢复、查询韵脚和导出文本。
- 从本地 MIDI/SVP 建立音节槽位后，可以完成一首歌词的编辑、版本切换、发音检查和新工程副本导出。
- 用户粘贴合法范围内的 URL 后，可以看到元数据、确认权利、下载、取消、重试、分析并删除受管理副本。
- 断网、URL 失效、哈希错误、磁盘不足和组件退出时，界面都有可操作的错误信息。
- AI 候选不会覆盖草稿，也不会在没有用户确认时写入 SynthV。

### 工程质量

- 所有写入路径都经过后端约束；符号链接/reparse point、路径穿越和未知组件均被拒绝。
- 下载器、媒体导入、项目存储、歌词检查和导出都有隔离测试，测试统一放在仓库根目录 `/test`。
- 安装、删除、重试、重启恢复和并发互斥都有可重复的契约测试。
- 不保存账号 Cookie、密码或平台令牌；日志对 URL 参数和用户路径做必要脱敏。
- 发布前分别验证源码、打包资源和已安装应用，不能只凭 TypeScript/Rust 单元测试宣称桌面功能可用。

## 用户操作简表

1. 打开“作词”，先选择“空白”或歌曲结构预设，写下创作简报和第一版草稿。
2. 如果已有 MIDI、SVP 或本地音频，从“工具箱”导入；先运行结构/发音检查，再建立音节约束。
3. 如果使用平台音频，进入“音频导入”，粘贴单个 URL，先查看元数据并完成权利确认，再开始下载。
4. 下载完成后选择分析能力；分析报告和标准化音频会进入当前歌曲项目，不覆盖原始来源。
5. 回到“作词”逐段写作；AI 只生成候选，人工点击“加入草稿”后再修改。
6. 完成后运行发音、韵脚和工程检查，创建检查点，最后导出歌词/LRC/MIDI 或新的 SynthV 工程副本。
7. 在“组件中心”查看组件版本和任务；失败时先重试或查看日志，删除时只会删除 Toolbox 管理的运行环境和缓存。

## 下一步

建议先实现第一阶段的歌曲项目持久化和本地作词闭环，再实现第二阶段的 `media-fetcher`。这样可以先验证“完整作词”本身的产品价值，同时把 Bilibili/YouTube 的不稳定解析和合规风险隔离在可替换组件中。
